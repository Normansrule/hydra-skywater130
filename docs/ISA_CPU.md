## Encodings that should be rejected

These are probes, not instructions: each is an encoding RV32IM
does not define. What the decoder does with them is a security
property, because a corrupted or fuzzed instruction stream should
trap rather than execute something.

| probe | opcode | funct3 | funct7 | legal | decoded as |
|---|---|---|---|---|---|
| (bad opcode) | `1111111` | 000 | 0000000 | **no** | rejected |
| (bad load f3) | `0000011` | 111 | 0000000 | yes | load |
| (bad store f3) | `0100011` | 111 | 0000000 | yes | store |
| (bad op f7) | `0110011` | 000 | 0100001 | yes | ALU ALU_SUB |

**3 of 4 undefined encodings decode as legal.**
The decoder checks the opcode but not every reserved funct
field, so an unallocated encoding executes as its nearest
neighbour instead of raising an illegal-instruction trap. On a
chip whose purpose includes security this is worth a decision:
either tighten the decode, or state that trapping is the
privileged-mode monitor's job and test that it happens.
